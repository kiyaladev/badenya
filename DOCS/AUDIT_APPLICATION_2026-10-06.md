# Audit de Badenya — 6 octobre 2026

**Verdict : l’application possède une bonne base, mais tout n’est pas fonctionnel ni cohérent. La version web en ligne est bloquée, plusieurs opérations financières produisent des états incohérents et certains boutons annoncent des actions qui ne sont pas réalisées. Je déconseille une ouverture à des utilisateurs réels avant les corrections prioritaires.**

L’audit couvre le serveur, l’administration, le site public et l’application Expo : lecture des routes, modèles, services, stores, écrans et configuration ; compilation ; tests ; essais HTTP sur une base MongoDB temporaire ; navigation Chromium ; contrôles de disposition à 375, 768 et 1440 pixels ; contrôle automatisé d’accessibilité avec axe-core. Les comptes et écritures utilisés pour les essais sont locaux et fictifs. La production a été consultée sans connexion ni modification de données.

Les preuves sont conservées dans [evidence.json](./audit-2026-10-06/evidence.json). Le code de départ comportait déjà de nombreuses modifications non commitées : les constats portent sur ce worktree, avec une vérification séparée de la version web déployée.

**Fonctions incomplètes ou trompeuses — établies par le code**

- **Découvrir et rejoindre un groupe ne fonctionne pas réellement.** Les quatre groupes publics sont écrits en dur. « Rejoindre avec un code » affiche « Demande envoyée » sans appeler le serveur. La demande d’adhésion publique modifie seulement un état React. Le code partagé correspond aux six derniers caractères de l’identifiant du groupe et aucun parcours serveur d’acceptation n’est raccordé à ces boutons. Source : [groups.tsx](/opt/apps/badenya/mobile/app/(tabs)/groups.tsx:36), [groups.tsx](/opt/apps/badenya/mobile/app/(tabs)/groups.tsx:109), [add-members.tsx](/opt/apps/badenya/mobile/app/(screens)/add-members.tsx:26).
- **Le tour de rôle des tontines est local à l’appareil.** Les modifications et confirmations de versement sont stockées dans AsyncStorage ; elles ne sont ni partagées avec les membres ni reliées à une transaction serveur. Le réordonnancement renumérote les tours sans remettre à jour le numéro du tour courant. Source : [tontine.service.ts](/opt/apps/badenya/mobile/services/tontine.service.ts:28). Pour une gestion collaborative, calendrier, autorisations et versements doivent avoir une source commune sur le serveur.
- **Les propositions n’ont pas de parcours complet de clôture dans le mobile.** L’API expose `/proposals/:id/close`, mais le service et les écrans mobiles examinés n’offrent pas cette action. Aucun traitement automatique de clôture n’a été trouvé. Le vote peut donc finir par refuser les nouveaux bulletins à l’échéance tout en laissant la proposition « pending ». Sources : [proposal.controller.ts](/opt/apps/badenya/backend/src/controllers/proposal.controller.ts:339), [proposal.service.ts](/opt/apps/badenya/mobile/services/proposal.service.ts:1), [proposal-details.tsx](/opt/apps/badenya/mobile/app/(screens)/proposal-details.tsx:1).
- **Le moteur de sondages séparé reste partiellement construit.** `participationRate` est fixé à 0 et les types quorum/unanimité ne changent pas le calcul du gagnant. `voteStore` et `vote.service` ne sont pas raccordés aux écrans : l’écran mobile « Voter » utilise les propositions. Source : [Vote.ts](/opt/apps/badenya/backend/src/models/Vote.ts:177). Clarifier s’il faut deux systèmes de vote ou un seul.
- **Le mode hors ligne risque de mélanger les comptes.** Cache et file d’attente utilisent des clés globales, sans identifiant utilisateur. La déconnexion supprime les jetons mais ne vide pas les stores, le cache et la file. Une action en attente peut ainsi être rejouée avec la session suivante. Les clés du cache ignorent aussi les paramètres des requêtes. Certaines erreurs 4xx sont supprimées de la file sans suivi visible ; un renouvellement de jeton échoué supprime les jetons même si la cause est réseau. Sources : [offline.service.ts](/opt/apps/badenya/mobile/services/offline.service.ts:5), [auth.service.ts](/opt/apps/badenya/mobile/services/auth.service.ts:143), [offlineStore.ts](/opt/apps/badenya/mobile/store/offlineStore.ts:49), [api.ts](/opt/apps/badenya/mobile/services/api.ts:63). Ce risque est constaté dans le code, pas reproduit sur un téléphone pendant cet audit.
- **La récupération du mot de passe est incomplète.** L’email pointe vers `/reset-password?token=…`, mais aucun écran de réinitialisation n’est présent dans les routes mobile, admin ou site public. L’environnement local du serveur ne configure pas d’envoi d’email et `APP_URL` est absent. Le service annonce néanmoins un succès quand aucun transport n’est disponible. Source : [email.service.ts](/opt/apps/badenya/backend/src/services/email.service.ts:106). Il faut un formulaire réellement accessible et un envoi vérifié.
- **Le contact perd le contenu et la newsletter n’est pas enregistrée.** Après correction du 401, le contrôleur ne conserve que les métadonnées et la longueur du message dans les logs ; il n’enregistre ni ne transmet son texte à l’équipe. La newsletter ne fait que journaliser l’adresse. Source : [contact.controller.ts](/opt/apps/badenya/backend/src/controllers/contact.controller.ts:15).
- **Les téléchargements et pages légales ne sont pas raccordés.** Les boutons App Store / Google Play pointent tous deux vers `/#download`, leur propre section. Les pages légales du site sont « bientôt ». Les liens mobiles utilisent un autre domaine. Sources : [HomePage.tsx](/opt/apps/badenya/landing-page/src/pages/HomePage.tsx:571), [Footer.tsx](/opt/apps/badenya/landing-page/src/components/Footer.tsx:101). Le serveur propose un APK nommé `badenya-debug.apk` : sa présence ne prouve pas qu’un build de distribution est prêt.
- **IA, push et biométrie doivent être présentés selon leur disponibilité réelle.** La configuration serveur examinée ne renseigne pas Gemini, Firebase ni email ; le mobile ne fournit pas de projet EAS dans `app.json`. Les services de notifications existent, mais les contrôleurs de création de groupe, cotisation et proposition examinés ne déclenchent pas leurs notifications métier. La préférence biométrique est enregistrée dans les paramètres sans contrôle correspondant trouvé à la connexion ou au retour dans l’application. Sources : [app.json](/opt/apps/badenya/mobile/app.json:1), [push-notification.service.ts](/opt/apps/badenya/mobile/services/push-notification.service.ts:51), [biometric.service.ts](/opt/apps/badenya/mobile/services/biometric.service.ts:1). La réception push et les capacités biométriques restent à tester sur appareils physiques.
- **La compatibilité web de l’authentification demande une adaptation supplémentaire.** Le client utilise SecureStore sans alternative web ; le module web installé expose un objet vide. Même après correction du bundle, ce parcours doit être vérifié. Source : [auth.service.ts](/opt/apps/badenya/mobile/services/auth.service.ts:2).

L’identité visuelle bleue, les cartes et les formulaires d’authentification sont lisibles et constituent une base à conserver. Le site public est correctement disposé aux largeurs testées de 375 et 1440 pixels. Les principaux défauts sont les suivants.

L’accessibilité automatisée relève des contrastes insuffisants dans le pied de page du site ; trois liens sociaux sans nom accessible sur Contact ; un bouton de réduction de navigation sans nom sur le dashboard ; des sélecteurs sans libellé sur Groupes et Transactions ; des contrastes insuffisants sur le dashboard. Les résultats du site ont été revérifiés après stabilisation des animations. Le menu mobile s’ouvre correctement et un déplacement au clavier a été vérifié. Cela ne constitue pas une validation complète au lecteur d’écran.

**Ce que je simplifierais, réorganiserais ou retirerais**

1. **Concentrer le produit sur les parcours fiables :** connexion → mes groupes → cotisation → validation → solde → proposition → vote → décision → dépense. Les invitations et la tontine partagée doivent compléter ces parcours avec des données serveur.
2. **Garder une navigation principale simple :** Accueil, Groupes, Transactions, Notifications, Profil. Dans un groupe : Résumé, Membres, Cotisations, Propositions, Tours et Rapports. L’action « Contribuer » doit toujours montrer le groupe concerné.
3. **Regrouper les écrans IA** dans une page d’analyse avec sections Synthèse, Recommandations et Anomalies ; ne les rendre disponibles que si le service est configuré. Les exports PDF/Excel restent dans Rapports.
4. **Centraliser les contrats et autorisations :** identifiants MongoDB, membres actifs, rôles, types de groupe, statut d’opération, enveloppe de réponse. Réduire les conversions et champs doublés (`user`/`userId`, `group`/`groupId`, réglages de cotisation aplatis et imbriqués).
5. **Employer un seul layout admin et les mêmes composants** pour recherche, chargement, erreur, confirmation, toast et pagination. Réutiliser les composants mobile en leur appliquant le thème effectif.
6. **Retirer ou masquer les éléments qui promettent une action inexistante :** faux groupes publics, faux succès d’adhésion, boutons de stores sans destination, bloc de statistiques vide, rubriques Blog/Carrières « bientôt », liens sociaux génériques. Remplacer la demande d’adhésion fictive par une vraie action ou un état explicite d’indisponibilité.
7. **Nettoyer les restes techniques inutilisés après vérification des imports :** `App.css` de template et `src/assets/react.svg` dans les deux applications Vite ; remplacer le favicon Vite admin avant de le supprimer ; supprimer ou implémenter `getMyTransactions()` qui retourne toujours `[]`. Décider du rôle du second système de sondages avant de retirer ses stores ou endpoints.
8. **Réduire les sources de vérité documentaires :** conserver un état actuel, un guide de démarrage, les contrats API et un guide de déploiement correspondant au serveur réel. Le README « prêt à déployer / 97,5 % » et le suivi « tous les items corrigés » sont contredits par cet audit. Les anciens états datés peuvent être archivés.
9. **Aligner l’exploitation :** les workflows citent `/var/www/badenya`, Vercel et plusieurs fichiers de verrouillage, tandis que le serveur actuel utilise `/opt/apps/badenya`, Nginx et PM2. Documenter la procédure réellement utilisée, les builds publiés et le retour à une version précédente. Le contrôle `/health` actuel ne teste pas l’état de la base ni les services facultatifs. Le job d’audit de dépendances masque les échecs avec `|| true`.

Ces propositions concernent le contenu trompeur, les doublons et le code inutilisé ; aucune suppression de données métier n’a été réalisée pendant l’audit.

**Ordre de correction recommandé**

| Étape | Résultat attendu | Vérifications nécessaires |
| --- | --- | --- |
| 1 — Accès | Web interactif, CORS valide, connexion admin sans boucle, suspension effective | Export web testé ; premier accès sans cookie ; rechargement d’une route protégée ; compte suspendu avec ancien jeton et nouvelle connexion |
| 2 — Comptabilité | Solde cohérent avec l’historique ; aucune double comptabilisation | Dépense sans solde refusée sans modification ; validation concurrente ; signalement d’une opération terminée ; réessai d’une même action |
| 3 — Parcours de groupe | Accès correct, vraie adhésion, calendrier partagé, proposition effectivement exécutée | Membre actif / suspendu / sorti ; invitation acceptée ; deux appareils pour une tontine ; clôture et exécution avec transaction |
| 4 — Services et offline | Réinitialisation utilisable, messages conservés, synchronisation liée au bon compte | Email reçu et lien utilisable ; contact conservé ; bascule compte A → B avec une file d’attente ; coupure réseau pendant renouvellement |
| 5 — Interface | Navigation homogène et lisible sur téléphone, tablette et bureau | Captures aux trois largeurs ; filtres et recherche ; totaux par groupe ; mode sombre ; accessibilité ; liens réels |

**Limites de vérification :** aucun téléphone Android/iOS ni simulateur natif n’a été utilisé ; l’APK n’a pas été installé. Paiements réels, délivrabilité email, push, biométrie, IA externe et comportement natif hors ligne ne sont pas validés de bout en bout. Les captures n’ont pas de baseline antérieure pour prouver une absence de régression visuelle, et les mesures de performance utilisateur en production n’ont pas été établies. La compilation et le rendu statique ne suffisent donc pas à qualifier ces fonctions de « fonctionnelles ».

**Décision : corriger les blocages d’accès et les incohérences financières en premier, puis terminer les parcours annoncés ; l’uniformisation visuelle vient ensuite.**
